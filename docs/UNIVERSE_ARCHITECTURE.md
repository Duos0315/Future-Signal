# FUTURE//SIGNAL — Living Universe Architecture

## Product definition
FUTURE//SIGNAL is a participatory digital evolution universe. Visitors explore a date-driven world, run transparent specialist agents, complete missions, design system blueprints, test those blueprints in synthetic models, and build a persistent record of discoveries.

Core loop: Discover a daily signal → interpret it through specialist perspectives → build a blueprint → experiment → record the outcome → contribute a proposal → return as the world changes.

## Implemented systems
- Daily generated signal and rolling public history in Git-tracked JSON.
- Four deterministic specialist roles: Scout, Systems Architect, Skeptic and Builder.
- Mission board with scan, prototype and simulation objectives.
- Creation bay for named habitat, swarm, city, energy and ecosystem blueprints.
- Stress tests using network, swarm and resource toy models.
- Local evolution progression, discovery log and JSON export.
- GitHub Issue Forms as a human-reviewed contribution path.

## GitHub Free architecture
GitHub Pages serves static HTML, CSS and JavaScript. GitHub Actions runs scheduled deterministic generation and tests. JSON files preserve public daily history. Browser modules execute simulations locally. GitHub Issues provide community proposals. No paid API or always-on server is required.

## Honest boundaries
- Agents are explainable deterministic roles. They do not independently research, browse or self-modify.
- The world changes by date and generated data; it is not a persistent 3D world simulation.
- XP is a local game mechanic, not scientific merit.
- Blueprints are structured concepts, not CAD models or deployable robotics.
- Simulation outputs are synthetic teaching models, not empirical findings or safety assurances.
- Browser localStorage is device-specific, not cloud sync or multiplayer.
- Community proposals require human review.

## Next evolution path
1. Versioned world schema with explicit biomes, resources, anomalies and daily modifiers.
2. Scenario engine with baseline, intervention and counterfactual comparisons.
3. Typed blueprint components, connections, constraints and resource budgets.
4. Evidence workflow with references, source quality, uncertainty and review status.
5. Human-reviewed contribution pipeline into approved JSON records.
6. Optional shared identity only if a backend or account-linked workflow becomes acceptable.

 
## Versioned world state (schema v1)
Every daily signal carries a `world` object with `version`, `cycle`, `biome`, `anomaly` and a `modifier`. The modifier is scoped to the generic pressure control and changes the initial lab setting; visitors can override it. World state is deterministic from the date and schema-validated with the signal.

## Controlled comparisons
The lab compares baseline and intervention scenarios with paired deterministic random streams. It reports mean and median paired deltas and counts improved, tied and declined trials. This is a reproducible comparison utility, not inferential statistics, a confidence interval or proof of causality.

## Blueprint module model
Each blueprint contains typed conceptual modules. Module inventory maps to bounded parameters for the relevant toy model. The mapping does not calculate physical dimensions, engineering loads, costs or safety.

## Evidence ledger
Visitors can attach HTTPS references to the current signal and label each as supporting, challenging or contextual, plus a source type. The browser validates URL format only. It does not fetch, authenticate, assess or verify source content. Entries are marked user-submitted and unverified; human review is required.
